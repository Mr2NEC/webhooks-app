# Webhooks App (тестове завдання Senior Frontend)

Вхід, список вебхуків з пагінацією та пошуком, редагування. API імітується через MSW за контрактом із завдання.

## Запуск

Потрібен Node.js 22+.

```bash
npm install
npm run dev          # http://localhost:5173
```

| Команда                             | Що робить                                                  |
| ----------------------------------- | ---------------------------------------------------------- |
| `npm test`                          | Vitest: тести сесії/CSRF + unit-тести параметрів URL       |
| `npm run typecheck`                 | `tsc -b` (strict)                                          |
| `npm run lint`                      | ESLint (`typescript-eslint` strictTypeChecked)             |
| `npm run build` / `npm run preview` | Production-збірка (мок увімкнений і в ній — бекенду немає) |

### Тестові облікові дані

```
Email:    demo@example.com
Пароль:   password123
```

Невірний пароль → 422 з помилкою біля поля «Пароль».

## Стек

React 19 + TypeScript (strict, `noUncheckedIndexedAccess`) · Vite · React Router · TanStack Query ·
react-hook-form + Yup · Mantine · MSW · Vitest.

## Архітектура

Модулі за фічами + ядро сесії у стилі ports & adapters: HTTP-клієнт не знає ні про React, ні про роутер,
ні про конкретний rotate-ендпоінт — залежності передаються в нього ззовні.

```
src/
  app/          composition root (services.ts), провайдери, маршрути, layout
  shared/
    api/        http-client (CSRF, 401→rotate, 419→recsrf), типізовані помилки
    lib/        single-flight, fingerprint
    forms/      applyServerErrors — 422 payload → поля форми
  features/
    auth/       api, session-store, auth-service, LoginPage, RequireAuth
    webhooks/   api, queries, list-params (URL ↔ стан), сторінки та компоненти
  mocks/        MSW: in-memory db, guards (XHR → CSRF → session), handlers
  test/         інтеграційні тести клієнта проти справжнього мока
```

Потік залежностей: `UI → hooks (TanStack Query) → api-функції → HttpClient → fetch`.
Шари з'єднуються лише в `app/services.ts`.

## Ключові рішення

### Сесія та повтори (`shared/api/http-client.ts`)

- **Один спільний rotate.** Усі запити, що отримали 401, чекають на один і той самий Promise (`singleFlight`).
- **Rotate не запускає rotate — гарантовано структурно.** `refreshSession` отримує окремий клієнт, який
  ніколи не оновлює сесію, тож рекурсія неможлива навіть якщо забути прапорець.
- **Epoch сесії.** Запит, відправлений до завершення rotate, але з 401, що прийшов після нього,
  просто повторюється — без другого rotate.
- **Межі повторів.** Повтори — це дві обгортки над однією спробою запиту: `retryOnCsrfMismatch` (419) і
  `retryOnUnauthorized` (401). Кожна повторює запит рівно один раз, без циклів і лічильників.
  Помилка rotate або повторний 401 → `onSessionExpired` → очищення кешу Query, сесії та редирект на вхід
  (зі збереженням поточної сторінки для повернення після входу).
- Тіло запиту серіалізується один раз — його можна безпечно надіслати повторно.
  Повтор `PUT` безпечний, бо мок перевіряє CSRF і сесію до виконання операції.
- TanStack Query не повторює API-помилки (це робить клієнт) — лише мережеві збої.

### Токени

- `device_session_token` живе лише в замиканні `authService.login` — не в store, не в URL, не в storage.
- `fingerprint` — 16 випадкових байтів (32 hex), один раз генерується і зберігається в `localStorage`
  (з fallback у пам'ять, якщо storage недоступний).
- Сесію клієнт не бачить: вона зберігається в моку (аналог HttpOnly-cookie). На старті застосунок
  питає `/v1/me` — так само він поводився б із реальною cookie. Після перезавантаження стан мока
  скидається, тому потрібен повторний вхід, а параметри списку з URL зберігаються.

### CSRF

`GET /csrf` виконується перед першим запитом (single-flight). Токен додається до POST/PUT/PATCH/DELETE.
На 419 токен перезапитується і запит повторюється один раз.

### URL списку

- URL — єдине джерело істини (`useListParams`). Невалідні значення (`?page=abc`, `?page=0`, `?limit=7`)
  нормалізуються через `replace`, параметри за замовчуванням не пишуться в URL.
- Розмір сторінки — 10 за замовчуванням (як у завданні), додатково можна обрати 25 або 50 (`?limit=`);
  зміна розміру скидає сторінку на 1.
- Список займає висоту вікна: прокручується лише тіло таблиці (заголовок «липкий»), а пошук і
  пагінація лишаються на місці — нічого не «стрибає» на неповній сторінці та під час пошуку.
- Пошук: локальна чернетка + debounce 300 мс → один запис в історії на кожен підтверджений пошук;
  зміна пошуку скидає сторінку на 1. На back/forward поле синхронізується з URL.
- Сторінка за межами `last` (застаріле посилання) коригується на останню через `replace`.
- `keepPreviousData` — під час переходу між сторінками таблиця не «блимає».

### Форми

RHF + Yup на клієнті перевіряють лише обов'язковість. Формат URL — правило сервера: 422 `payload`
розкладається по полях через `applyServerErrors`, невідомі поля потрапляють у загальну помилку форми.

### Редагування в модальному вікні

Модальне вікно — це вкладений маршрут `/webhooks/:id` поверх списку: у нього є власна адреса
(працюють пряме посилання, перезавантаження та «назад»), а параметри списку лишаються в URL,
тож після закриття список повертається на ту саму сторінку з тим самим пошуком.
Після успішного збереження вікно закривається; при помилці 422 лишається відкритим із помилками біля полів.

## Тести

`src/test/session-rotation.test.ts` — справжній `HttpClient` проти справжніх MSW-хендлерів,
керований годинник мока (без очікування 30 с):

- **два паралельні запити з 401 → один rotate → успішні повтори** (обов'язковий тест);
- помилка rotate → обидва запити отримують `SessionExpiredError`, `onSessionExpired` викликається один раз;
- повторний 401 після rotate → завершення сесії;
- CSRF перед першим запитом; 419 → новий токен → один повтор; другий 419 не повторюється;
- 422 з помилками полів, пошук без урахування регістру.
